## 1. THE FEATURE MAP ENGINE (`src/models/kernel.py`)

The `TaylorFeatureMap` class implements a deterministic 2nd-degree polynomial mapping $\phi(\mathbf{x}): \mathbb{R}^d \to \mathbb{R}^{d'}$ that maps the input query and key projections into a linearized kernel space.

### 1.1 Constructor Block

```python
class TaylorFeatureMap(nn.Module):
    def __init__(self, head_dim: int, scale_input: bool = True) -> None:
        super().__init__()
        self.d           = head_dim
        self.scale_input = scale_input
        self.d_prime     = 1 + head_dim + head_dim * (head_dim + 1) // 2
```

#### Mathematical Formulation
The feature dimension $d'$ is defined as:
$$d' = 1 + d + \frac{d(d + 1)}{2}$$

For $d = 16$:
$$d' = 1 + 16 + \frac{16 \times 17}{2} = 1 + 16 + 136 = 153$$

#### Memory State Transitions
1. Instantiates a class instance on the CPU.
2. Allocates three scalar attributes in the Python object dictionary: `self.d` (int, 8 bytes), `self.scale_input` (bool, 1 byte), and `self.d_prime` (int, 8 bytes).

---

### 1.2 Upper-Triangular Index Generation

```python
        rows, cols = torch.triu_indices(head_dim, head_dim, offset=0)
        self.register_buffer("triu_rows", rows)   # (n_quad,)
        self.register_buffer("triu_cols", cols)   # (n_quad,)
```

#### Mathematical Formulation
The indexing constraints represent the set of all unique quadratic monomials $x_i x_j$ for $i \le j$ where $i, j \in \{1, \dots, d\}$. The indices are generated by:
$$\mathcal{I}_{\text{triu}} = \left\{ (i, j) \mid 0 \le i \le j < d \right\}$$

The total number of elements in $\mathcal{I}_{\text{triu}}$ is the sum of the arithmetic progression from $1$ to $d$:
$$|\mathcal{I}_{\text{triu}}| = \sum_{k=1}^d k = \frac{d(d+1)}{2}$$

For $d = 16$, the set size is:
$$|\mathcal{I}_{\text{triu}}| = \frac{16(17)}{2} = 136 \text{ indices}$$

#### Memory State Transitions
1. `torch.triu_indices` allocates two contiguous 1D `int64` tensors `rows` and `cols` in PyTorch memory of shape `[136]`.
2. Memory: $136 \text{ elements} \times 8 \text{ bytes/element} = 1,088 \text{ bytes}$ per tensor.
3. `register_buffer` binds these tensors to the module state dict, ensuring they migrate to the target hardware device (CPU/GPU) automatically during `.to(device)` calls without registering them as learnable parameters.

---

### 1.3 Scaling Scale Coefficients

```python
        quad_scale = torch.where(
            rows == cols,
            torch.ones(len(rows)),
            torch.full((len(rows),), math.sqrt(2.0)),
        )
        self.register_buffer("quad_scale", quad_scale)  # (n_quad,)
```

#### Mathematical Formulation
The quadratic block of the inner product is:
$$\phi(\mathbf{q})^\top \phi(\mathbf{k}) \supseteq \sum_{i=1}^d \phi_i(\mathbf{q}) \phi_i(\mathbf{k})$$

To reconstruct the algebraic identity $1 + \mathbf{q}^\top \mathbf{k} + \left(\mathbf{q}^\top \mathbf{k}\right)^2$ without the $\frac{1}{2}$ scale factor on the quadratic term, the diagonal terms $q_i^2 k_i^2$ must carry a coefficient of $1.0$, while the off-diagonal terms $2q_i q_j k_i k_j$ must carry a coefficient of $2.0$.
Evaluating the inner product of the feature map components:
$$\left( c_i x_i x_j \right) \left( c_i y_i y_j \right) = c_i^2 x_i x_j y_i y_j$$

For diagonal indices $i = j$:
$$c_{\text{diag}}^2 = 1 \implies c_{\text{diag}} = 1.0$$
For off-diagonal indices $i < j$:
$$c_{\text{off\_diag}}^2 = 2 \implies c_{\text{off\_diag}} = \sqrt{2}$$

Thus, the scaling coefficient vector $\mathbf{w} \in \mathbb{R}^{n_{\text{quad}}}$ is:
$$w_k = \begin{cases} 1.0 & \text{if } \text{rows}[k] = \text{cols}[k] \\ \sqrt{2} & \text{if } \text{rows}[k] < \text{cols}[k] \end{cases}$$

#### Memory State Transitions
1. `torch.ones` and `torch.full` allocate temporary vectors of size `[136]` (FP32, 544 bytes).
2. `torch.where` evaluates a logical comparison over the CPU registers and returns a contiguous float32 tensor `quad_scale` of shape `[136]` (544 bytes).
3. Registered as a buffer and stored in PyTorch tensor cache.

### 1.4 Normalized Input Projections

```python
    def forward(self, x: torch.Tensor) -> torch.Tensor:
        ...
        B, H, T, d = x.shape
        ...
        if self.scale_input:
            x = x / math.sqrt(d)
```

#### Mathematical Formulation
To prevent the polynomial components from scaling exponentially with the head dimension $d$, the input projections are divided by the square root of the head dimension:
$$\mathbf{x}_{\text{norm}} = \frac{\mathbf{x}}{\sqrt{d}}$$

For $d = 16$, the tensor division is:
$$x_{b,h,t,i} \leftarrow \frac{x_{b,h,t,i}}{4}$$

This scaling keeps the dot product $\mathbf{q}^\top \mathbf{k} \sim O(1)$, keeping the downstream quadratic values stable.

#### Memory State Transitions
1. `x.shape` fetches a tuple of dimensions `[B, H, T, d]` from the PyTorch C++ tensor metadata (no allocation).
2. If `scale_input` is True, PyTorch allocates a new tensor of shape `[B, H, T, d]` to store the quotient (size: $B \cdot H \cdot T \cdot d \cdot 4 \text{ bytes}$) and registers the division operation in the Autograd backward graph.

2. `linear = x` creates a Python reference alias pointing to the memory allocation of `x` (0-copy view operation).

### 1.6 Vectorized 4D Slice Selection Patch

```python
        # Original Naive 5D Outer Product (Line 156-161):
        # x_outer = x.unsqueeze(-1) * x.unsqueeze(-2)
        # quad = x_outer[..., self.triu_rows, self.triu_cols]

        # Vectorized 4D Slice Selection (Patched):
        quad = (x[..., self.triu_rows] * x[..., self.triu_cols]) * self.quad_scale
```

#### Mathematical Formulation
For each sequence index $t$, the quadratic term extracts the upper-triangular components of the outer product matrix $\mathbf{x}_t \mathbf{x}_t^\top \in \mathbb{R}^{d \times d}$. 

The naive formulation constructs the full outer product matrix:
$$X_{\text{outer}, b,h,t,i,j} = x_{b,h,t,i} \cdot x_{b,h,t,j}$$
and then indexes it using two index vectors:
$$\text{quad}_{b,h,t,k} = X_{\text{outer}, b,h,t,u_k,v_k} \cdot w_k$$

The 4D slice patch bypasses this intermediate matrix by indexing the vector directly:
$$\text{quad}_{b,h,t,k} = \left( x_{b,h,t,u_k} \cdot x_{b,h,t,v_k} \right) \cdot w_k$$
where $u_k = \text{triu\_rows}[k]$ and $v_k = \text{triu\_cols}[k]$ for $k \in \{0, \dots, 135\}$.

#### Memory State Transitions & Optimization Proof
1. **Naive 5D Outer Product Allocation**:
   - `x.unsqueeze(-1)` creates a view of shape `[B, H, T, d, 1]`.
   - `x.unsqueeze(-2)` creates a view of shape `[B, H, T, 1, d]`.
   - The element-wise multiplication broadcasts these shapes and allocates a new 5D tensor `x_outer` of shape `[B, H, T, d, d]`.
   - For $B=32, H=4, T=1440, d=16$, the memory required is:
     $$\text{Memory}_{5D} = 32 \times 4 \times 1440 \times 16 \times 16 \times 4 \text{ bytes} = 188,743,680 \text{ bytes} \approx 188.74 \text{ MB}$$
   - Extracting `x_outer[..., self.triu_rows, self.triu_cols]` triggers advanced indexing, allocating another tensor of shape `[B, H, T, 136]` (100.27 MB).
   - Total peak memory for naive outer product: **289.01 MB**.

2. **4D Vectorized Patch Allocation**:
   - `x[..., self.triu_rows]` indexes `x` along the last dimension using a 1D tensor buffer of shape `[136]`, creating a view of shape `[B, H, T, 136]`.
   - `x[..., self.triu_cols]` creates a view of shape `[B, H, T, 136]`.
   - PyTorch performs element-wise multiplication between the two slices and scales the result by `self.quad_scale`.
   - Peak allocation is limited to the output tensor of shape `[B, H, T, 136]`:
     $$\text{Memory}_{4D} = 32 \times 4 \times 1440 \times 136 \times 4 \text{ bytes} = 100,270,080 \text{ bytes} \approx 100.27 \text{ MB}$$
   - This eliminates the intermediate 5D tensor, reducing memory footprint by:
     $$\Delta \text{Memory} = 188.74 \text{ MB} \quad (\text{a 65.3\% peak memory saving})$$

### 1.7 Block Concatenation

```python
        return torch.cat([ones, linear, quad], dim=-1)
```

#### Mathematical Formulation
The final feature vector $\phi(\mathbf{x}) \in \mathbb{R}^{d'}$ is constructed by concatenating the three blocks along the last axis:
$$\phi(\mathbf{x}) = \text{concat}\left( \mathbf{ones}, \, \mathbf{linear}, \, \mathbf{quad} \right) \in \mathbb{R}^{B \times H \times T \times d'}$$
$$\phi(\mathbf{x}) = \begin{bmatrix} 1 & x_1 & \dots & x_d & x_1^2 & \dots & \sqrt{2}x_{d-1}x_d \end{bmatrix}^\top$$

#### Memory State Transitions
1. `torch.cat` allocates a contiguous float32 tensor of shape `[B, H, T, d']` = `[32, 4, 1440, 153]`.
2. Memory: $32 \times 4 \times 1440 \times 153 \times 4 \text{ bytes} = 112,803,840 \text{ bytes} \approx 112.80 \text{ MB}$.
3. Copies the elements from `ones` (0.74 MB), `linear` (11.80 MB), and `quad` (100.27 MB) into this contiguous block.
4. Temporary variables `ones` and `quad` are marked for deallocation.

## 2. THE ASSOCIATIVE ATTENTION CONTRACTION (`src/models/linear_attention.py`)

This file implements the $O(T)$ associative multi-head attention mechanism.

### 2.1 Feature Mapping of Queries and Keys

```python
        Q_phi: torch.Tensor = self.phi(Q)   # φ(Q)
        K_phi: torch.Tensor = self.phi(K)   # φ(K)
```

#### Mathematical Formulation
Maps the projected query tensor $\mathbf{Q} \in \mathbb{R}^{B \times H \times T \times d}$ and key tensor $\mathbf{K} \in \mathbb{R}^{B \times H \times T \times d}$ to the expanded feature representations $\Phi(\mathbf{Q}), \Phi(\mathbf{K}) \in \mathbb{R}^{B \times H \times T \times d'}$:
$$\Phi(\mathbf{Q})_{b,h,t,:} = \phi(\mathbf{q}_{b,h,t}), \quad \Phi(\mathbf{K})_{b,h,t,:} = \phi(\mathbf{k}_{b,h,t})$$

#### Memory State Transitions
1. Executes `TaylorFeatureMap.forward` for `Q` and `K` sequentially.
2. Allocates two tensors `Q_phi` and `K_phi` of shape `[B, H, T, d']` on the target device.
3. Memory: $2 \times 112.80 \text{ MB} = 225.60 \text{ MB}$.

---

### 2.2 Key-Value State Tensor Construction

```python
        KV_state: torch.Tensor = torch.einsum("bhtp, bhtv -> bhpv", K_phi, V)
```

#### Mathematical Formulation
The intermediate key-value state tensor $\mathbf{S}$ aggregates the outer products of keys and values over the sequence length axis:
$$\mathbf{S}_{b, h, p, v} = \sum_{t=1}^T \Phi(\mathbf{K})_{b, h, t, p} \cdot \mathbf{V}_{b, h, t, v}$$
where $p \in \{1, \dots, d'\}$ and $v \in \{1, \dots, d_v\}$.

#### Memory State Transitions
1. The `einsum` engine parses the index string `bhtp, bhtv -> bhpv`.
2. It detects that the temporal index `t` appears in both inputs but not in the output, which triggers an inner product reduction along the time axis $T$.
3. Allocates a contiguous tensor `KV_state` of shape `[B, H, d_prime, d_v]` = `[32, 4, 153, 16]`.
4. Memory: $32 \times 4 \times 153 \times 16 \times 4 \text{ bytes} = 1,253,376 \text{ bytes} \approx 1.25 \text{ MB}$.
5. This collapses the sequence dimension $T=1440$, reducing memory usage relative to standard attention:
   $$\text{Memory Complexity} = O(B \cdot H \cdot d' \cdot d_v) \quad (\text{independent of sequence length } T)$$

---

### 2.3 Context Retrieval

```python
        Context: torch.Tensor = torch.einsum("bhtp, bhpv -> bhtv", Q_phi, KV_state)
```

#### Mathematical Formulation
The unnormalized output for each query position is computed by contracting the query features with the aggregated key-value state matrix:
$$\text{Context}_{b, h, t, v} = \sum_{p=1}^{d'} \Phi(\mathbf{Q})_{b, h, t, p} \cdot \mathbf{S}_{b, h, p, v}$$

#### Memory State Transitions
1. The `einsum` engine contracts the tensors over the feature dimension `p` (153).
2. Allocates a contiguous float32 tensor `Context` of shape `[B, H, T, d_v]` = `[32, 4, 1440, 16]`.
3. Memory: $32 \times 4 \times 1440 \times 16 \times 4 \text{ bytes} = 11,796,480 \text{ bytes} \approx 11.80 \text{ MB}$.

---

### 2.4 Partition Normalization Floor

```python
        # Step 4a: Sum K_phi over the time axis
        K_phi_sum: torch.Tensor = K_phi.sum(dim=2)   # Σ_t φ(K)

        # Step 4b: Inner product of each Q feature vector with the key mass
        denominator: torch.Tensor = torch.einsum("bhtp, bhp -> bht", Q_phi, K_phi_sum)
```

#### Mathematical Formulation
The normalization denominator $Z_t$ is the partition function of the linearized softmax kernel, ensuring the attention weights sum to 1:
$$Z_{b, h, t} = \sum_{t'=1}^T \Phi(\mathbf{Q})_{b, h, t, :}^\top \Phi(\mathbf{K})_{b, h, t', :}$$
$$Z_{b, h, t} = \Phi(\mathbf{Q})_{b, h, t, :}^\top \left( \sum_{t'=1}^T \Phi(\mathbf{K})_{b, h, t', :} \right)$$

This is implemented by first summing the keys along the time dimension:
$$\mathbf{k\_sum}_{b, h, p} = \sum_{t=1}^T \Phi(\mathbf{K})_{b, h, t, p}$$
and then taking the dot product with the queries:
$$Z_{b, h, t} = \sum_{p=1}^{d'} \Phi(\mathbf{Q})_{b, h, t, p} \cdot \mathbf{k\_sum}_{b, h, p}$$

#### Mathematical Proof of the Safety Floor
Under complete signal loss in the grid, all input keys drop to zero:
$$\mathbf{k}_{t'} = \mathbf{0} \in \mathbb{R}^d \quad \forall t'$$

Passing this zero vector through the 2nd-degree Taylor feature map $\phi(\mathbf{x})$:
$$\phi(\mathbf{0}) = \begin{bmatrix} 1 & 0 & \dots & 0 \end{bmatrix}^\top \in \mathbb{R}^{d'}$$

Summing these feature-mapped keys over sequence length $T$:
$$\mathbf{k\_sum}_{b, h} = \sum_{t'=1}^T \phi(\mathbf{0}) = \begin{bmatrix} \sum_{t'=1}^T 1 \\ \sum_{t'=1}^T 0 \\ \vdots \\ \sum_{t'=1}^T 0 \end{bmatrix} = \begin{bmatrix} T \\ 0 \\ \vdots \\ 0 \end{bmatrix}$$

Evaluating the denominator $Z_{b,h,t}$ for any query features $\Phi(\mathbf{Q})_{b,h,t,:} = [1, \, q_{t,1}, \, \dots, \, q_{t,d'-1}]^\top$:
$$Z_{b,h,t} = \Phi(\mathbf{Q})_{b,h,t,:}^\top \mathbf{k\_sum}_{b,h} = 1 \cdot T + q_{t,1} \cdot 0 + \dots + q_{t,d'-1} \cdot 0 = T$$

Since sequence length $T \ge 1$, the partition function has a strict lower bound:
$$Z_{b,h,t} \ge T > 0$$

For $T = 1440$, the denominator evaluates to $1440.0$, making division-by-zero or numerical overflow impossible even without an artificial epsilon guard $\varepsilon$.

#### Memory State Transitions
1. `K_phi.sum(dim=2)` allocates a tensor `K_phi_sum` of shape `[B, H, d_prime]` = `[32, 4, 153]`. Memory: $32 \times 4 \times 153 \times 4 \text{ bytes} \approx 78.3 \text{ KB}$.
2. `torch.einsum` contracts the tensors over the `p` axis, allocating a tensor `denominator` of shape `[B, H, T]` = `[32, 4, 1440]`. Memory: $32 \times 4 \times 1440 \times 4 \text{ bytes} \approx 737.3 \text{ KB}$.

---

### 2.5 Safe Normalization Division

```python
        output: torch.Tensor = Context / (denominator.unsqueeze(-1) + self.eps)
```

#### Mathematical Formulation
The unnormalized context is scaled by the reciprocal of the denominator:
$$\text{Output}_{b,h,t,v} = \frac{\text{Context}_{b,h,t,v}}{Z_{b,h,t} + \varepsilon}$$

where $\varepsilon$ is a safety constant (`self.eps = 1e-6`).

#### Memory State Transitions
1. `denominator.unsqueeze(-1)` creates a view of shape `[B, H, T, 1]` (0-copy).
2. The addition `+ self.eps` allocates a temporary tensor of shape `[B, H, T, 1]` (737.3 KB).
3. The division operation broadcasts the denominator tensor along the value axis $v$, allocating the final output tensor `output` of shape `[B, H, T, d_v]` = `[32, 4, 1440, 16]`. Memory: **11.80 MB**.

## 3. THE SPATIAL-TEMPORAL BASELINE (`src/models/cdlinear.py`)

The `CDLinearBaseline` model models joint spatial-temporal correlations by flattening the time and channel axes into a unified feature vector.

### 3.1 Constructor and Weight Initialization

```python
class CDLinearBaseline(nn.Module):
    def __init__(self, seq_len: int = 1440, pred_len: int = 60, channels: int = 7) -> None:
        super().__init__()
        ...
        self.linear = nn.Linear(seq_len * channels, pred_len * channels)
        self._init_weights()

    def _init_weights(self) -> None:
        nn.init.xavier_uniform_(self.linear.weight)
        nn.init.zeros_(self.linear.bias)
```

#### Mathematical Formulation
Let $\mathbf{W} \in \mathbb{R}^{d_{\text{out}} \times d_{\text{in}}}$ be the weights and $\mathbf{b} \in \mathbb{R}^{d_{\text{out}}}$ be the bias, where:
$$d_{\text{in}} = L_{\text{seq}} \cdot C = 1440 \times 7 = 10,080 \text{ features}$$
$$d_{\text{out}} = L_{\text{pred}} \cdot C = 60 \times 7 = 420 \text{ features}$$

The weights are initialized using a uniform Xavier distribution:
$$W_{i, j} \sim \mathcal{U}(-a, a) \quad \text{where } a = \sqrt{\frac{6}{d_{\text{in}} + d_{\text{out}}}}$$
$$a = \sqrt{\frac{6}{10,080 + 420}} = \sqrt{\frac{6}{10,500}} \approx 0.0239045$$

The bias vector is initialized to zero:
$$b_k = 0 \quad \forall k \in \{1, \dots, 420\}$$

#### Memory State Transitions
1. Instantiates the baseline model on the CPU.
2. Allocates the weight parameter matrix `self.linear.weight` of shape `[420, 10080]`.
   $$\text{Weight Memory} = 420 \times 10,080 \times 4 \text{ bytes} = 16,934,400 \text{ bytes} \approx 16.93 \text{ MB}$$
3. Allocates the bias vector `self.linear.bias` of shape `[420]`.
   $$\text{Bias Memory} = 420 \times 4 \text{ bytes} = 1,680 \text{ bytes}$$

---

### 3.2 Slicing and Flattening

```python
    def forward(self, x: torch.Tensor) -> torch.Tensor:
        B, T, C = x.shape
        x_flat = x.reshape(B, -1)
```

#### Mathematical Formulation
The input tensor $\mathbf{X} \in \mathbb{R}^{B \times T \times C}$ is vectorized row-wise across the time and channel dimensions:
$$\mathbf{x}_{\text{flat}, b} = \text{vec}(\mathbf{X}_{b, :, :}) = \begin{bmatrix} X_{b, 1, 1} & \dots & X_{b, 1, C} & X_{b, 2, 1} & \dots & X_{b, T, C} \end{bmatrix}^\top \in \mathbb{R}^{T \cdot C}$$

#### Memory State Transitions
1. `x.shape` fetches dimensions `[32, 1440, 7]` from the C++ metadata.
2. `x.reshape(B, -1)` flattens the last two dimensions. If the input tensor `x` is contiguous in memory, this returns a **0-copy view** of shape `[32, 10080]`. If the layout is non-contiguous, PyTorch allocates a new memory block of the same size (0.90 MB) and copies the elements over.

---

### 3.3 Linear Projection and Reshaping

```python
        out_flat = self.linear(x_flat)
        return out_flat.reshape(B, self.pred_len, self.channels)
```

#### Mathematical Formulation
The linear mapping projects the flattened history into the forecast horizon:
$$\mathbf{y}_{\text{flat}, b} = \mathbf{W} \mathbf{x}_{\text{flat}, b} + \mathbf{b} \quad \in \mathbb{R}^{d_{\text{out}}}$$

This result is then folded back into the sequence shape:
$$\mathbf{Y}_{b, t, c} = y_{\text{flat}, b, \, (t - 1) \cdot C + c} \quad \in \mathbb{R}^{B \times L_{\text{pred}} \times C}$$
where $t \in \{1, \dots, 60\}$ and $c \in \{1, \dots, 7\}$.

#### Parameter Footprint Audit & Inductive Bias
* **Total Parameters**:
  $$\text{Total Parameters} = d_{\text{in}} \cdot d_{\text{out}} + d_{\text{out}} = 10,080 \times 420 + 420 = 4,234,020 \text{ parameters}$$
* **Inductive Bias Comparison**:
  `CDLinear` maps every input point directly to every output point via a static weight matrix. This allows it to learn fixed temporal relationships and physical cross-channel correlations directly (e.g., how load on sub-meter 1 at 12:00 PM correlates with sub-meter 3 at 1:00 PM).
  Conversely, the `LinearGridTransformer` uses dynamic query-key matching to compute attention coefficients at runtime. This routes information dynamically based on the input features, giving it the flexibility to capture variable temporal patterns at the cost of requiring more training data to converge on fixed correlations.

#### Memory State Transitions
1. `self.linear(x_flat)` executes a matrix multiplication `GEMM` on the CPU:
   $$\mathbf{Y}_{\text{flat}} = \mathbf{X}_{\text{flat}} \mathbf{W}^\top + \mathbf{b}$$
   This allocates an intermediate tensor `out_flat` of shape `[32, 420]`. Memory: $32 \times 420 \times 4 \text{ bytes} = 53,760 \text{ bytes} \approx 53.7 \text{ KB}$.
2. `out_flat.reshape(B, 60, 7)` returns a view of shape `[32, 60, 7]`.

### 4.2 Strided Block Accumulation & Crossover Protection

```python
            for _, group in df_split.groupby(["_year", "_month"], sort=True):
                # Target length: 1 week (10,080 minutes) for train, 2 days (2,880 minutes) for val
```

#### Mathematical Formulation

where:

#### Memory State Transitions
1. `df_split.groupby` indexes the DataFrame by year and month.
2. `group.head` slices the first $L_{\text{target}}$ rows of each group, allocating a smaller DataFrame.
3. `to_numpy(dtype=np.float32, copy=False)` returns a contiguous float32 NumPy array view `block_arr` of shape `[L_actual, 7]`. Memory size for a full 1-week block:
   $$\text{Block Memory} = 10,080 \times 7 \times 4 \text{ bytes} = 282,240 \text{ bytes} \approx 282.2 \text{ KB}$$

### 4.3 Crossover Boundary Protection Mapper

```python
                # Valid starting positions for block i of length L_i at a given current_offset:
                # [current_offset, current_offset + L_i - self._window]
                if block_len >= self._window:
                    for i in range(block_len - self._window + 1):
                        valid_indices.append(current_offset + i)

                current_offset += block_len

            self._data = np.concatenate(blocks, axis=0)
            self._valid_indices = np.array(valid_indices, dtype=np.int64)
```

#### Mathematical Formulation
Let the concatenated array `self._data` contain $M$ independent blocks. The $k$-th block starts at index $O_k = \sum_{j=1}^{k-1} L_j$ and has length $L_k$. 

The sliding window length is:
$$W = L_{\text{lookback}} + L_{\text{forecast}} = 1440 + 60 = 1500 \text{ steps}$$

If a sliding window starts at index $s$, the lookback window covers $[s, s + L_{\text{lookback}} - 1]$ and the forecast window covers $[s + L_{\text{lookback}}, s + W - 1]$. 

To prevent the window from spanning across discontinuous monthly block boundaries, the window must lie completely within a single block:
$$[s, s + W - 1] \subset [O_k, O_k + L_k - 1]$$

This constraint is enforced by limiting the valid starting indices to:
$$s \in \bigcup_{k=1}^M \left\{ O_k, O_k + 1, \dots, O_k + L_k - W \right\}$$

Any start index $s$ that violates this constraint (i.e., lies in the boundary region $[O_k + L_k - W + 1, O_k + L_k - 1]$) is excluded from `self._valid_indices`, preventing data leakage and non-causal temporal jumps.

#### Memory State Transitions
1. `np.concatenate(blocks, axis=0)` copies all individual block arrays into a single contiguous C-ordered float32 array `self._data` of shape `[N_total_subsampled, 7]`.
2. `np.array(valid_indices, dtype=np.int64)` allocates a contiguous 1D array of valid starting indices.

### 4.4 Lazy Slice Z-Score Normalization

```python
    def __getitem__(self, idx: int) -> Tuple[torch.Tensor, torch.Tensor]:
        ...
        start = self._valid_indices[idx]
        mid   = start + self.t_lookback
        end   = mid   + self.t_forecast

        x_raw: np.ndarray = self._data[start:mid]   # (T_lookback, 7)
        y_raw: np.ndarray = self._data[mid:end]      # (T_forecast, 7)

        x_norm = (x_raw - self._mean) / self._std    # (T_lookback, 7)
        y_norm = (y_raw - self._mean) / self._std    # (T_forecast, 7)

        return (
            torch.from_numpy(x_norm.copy()),
            torch.from_numpy(y_norm.copy()),
        )
```

#### Mathematical Formulation
The raw slices are normalized using the pre-computed training mean $\boldsymbol{\mu} \in \mathbb{R}^7$ and standard deviation $\boldsymbol{\sigma} \in \mathbb{R}^7$:
$$x_{\text{norm}, t, c} = \frac{x_{\text{raw}, t, c} - \mu_c}{\sigma_c}$$
$$y_{\text{norm}, t, c} = \frac{y_{\text{raw}, t, c} - \mu_c}{\sigma_c}$$

#### Memory State Transitions
1. `self._data[start:mid]` returns a **zero-copy view** of the array.
2. The subtraction and division operations allocate two new float32 NumPy arrays `x_norm` (shape `[1440, 7]`, 40.3 KB) and `y_norm` (shape `[60, 7]`, 1.68 KB).
3. `x_norm.copy()` and `y_norm.copy()` create contiguous copies of the arrays in memory.
4. `torch.from_numpy` creates PyTorch tensors that share memory with the contiguous NumPy arrays (0-copy view operation).

## 5. THE RUNTIME HARDWARE OPTIMIZER (`train_comparative.py`)

This script manages training execution, memory usage, and CPU thread pools.

### 5.1 CPU Thread Pool Configurations

```python
cores = os.cpu_count() or 4
import torch
torch.set_num_threads(cores)
torch.set_num_interop_threads(2)
```

#### Operational Mechanics
When running on multi-core CPU architectures (such as Intel x86 Xeon or Core CPUs), PyTorch default parallelization can run into resource contention.

1. **Intra-op Parallelism (`set_num_threads`)**:
   Sets the number of threads used for parallelizing individual operators (such as the CDLinear matrix multiplication) via OpenMP/MKL.
   If set to the logical core count (which includes Hyper-Threading cores), multiple threads compete for the same physical execution units. This leads to thread context switching and invalidates L1/L2 caches.
   Setting `num_threads = cores` (matching the physical core count) ensures each thread is pinned to a physical core, maximizing the hit rate of CPU L3 cache lines.
2. **Inter-op Parallelism (`set_num_interop_threads`)**:
   Sets the threads available for executing independent operations in the computation graph in parallel. Setting this to `2` limits parallel thread scheduling overhead.

#### Memory Cache Line Behavior
The CDLinear weight matrix is of size $420 \times 10,080$ (16.93 MB), which fits within typical L3 caches (typically $24\text{MB} - 45\text{MB}$ on modern CPUs). 

Limiting active threads to the physical core count ensures the weight matrix can be loaded into L3 cache and shared efficiently without experiencing MESI cache invalidations from thread scheduling overhead.

### 5.2 Dynamic Module Monkey Patching

```python
# ── Monkey-Patch TaylorFeatureMap to avoid huge 5D outer-product and slow advanced indexing ──
def patched_forward(self, x: torch.Tensor) -> torch.Tensor:
    ...
    ones = x.new_ones(B, H, T, 1)
    linear = x
    quad = (x[..., self.triu_rows] * x[..., self.triu_cols]) * self.quad_scale
    return torch.cat([ones, linear, quad], dim=-1)

TaylorFeatureMap.forward = patched_forward
```

#### Operational Mechanics
This overrides the `forward` method of `TaylorFeatureMap` globally at runtime. When `LinearGridForecaster` or `LinearKernelAttention` is instantiated, they call this optimized version, bypassing the naive 5D outer product allocations and the associated advanced indexing memory overhead.

### 5.3 Active Autograd Cleanups

```python
        for batch_idx, (x, y) in enumerate(loader):
            ...
            optimizer.zero_grad(set_to_none=True)
            pred = model(x)
            loss = criterion(pred, y)
            loss.backward()
            nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
            optimizer.step()
            ...
            del loss, pred, x, y
```

#### Mathematical Formulation
The gradient clipping operation scales the gradients if their joint $L_2$ norm exceeds a threshold $c = 1.0$:
$$\mathbf{g} \leftarrow \mathbf{g} \cdot \min\left(1, \, \frac{c}{\|\mathbf{g}\|_2}\right)$$
where $\|\mathbf{g}\|_2 = \sqrt{\sum_{\theta} \|\nabla_{\theta} \mathcal{L}\|_2^2}$.

#### Memory State Transitions
1. `optimizer.zero_grad(set_to_none=True)`:
   - Instead of writing zeros to the gradient tensors (`.grad = 0.0`), this deletes the gradient attributes by setting them to `None`.
   - This frees the associated memory buffers immediately, reducing the active memory footprint during the forward pass.
2. `loss.backward()`:
   - Evaluates the chain rule backward through the computation graph.
   - Allocates temporary gradient tensors for all intermediate activations.
3. `clip_grad_norm_`:
   - Computes the $L_2$ norm of the parameter gradients, allocating a scalar tensor.
4. `del loss, pred, x, y`:
   - Deletes Python references to the intermediate tensors in the local loop scope.
   - This allows PyTorch's C++ memory manager to reclaim the memory buffers immediately without waiting for the next loop iteration.

### 5.4 Epoch Garbage Collection

```python
        # End of epoch: clear transient allocations and collect garbage
        gc.collect()
```

#### Operational Mechanics
Although PyTorch's C++ allocator manages tensor memory pools, Python's reference counting and cyclic garbage collector manage the Python-side object wrappers. 

During training loops, circular references can accumulate in the autograd history or python exception frames, keeping tensors in memory. Calling `gc.collect()` forces a garbage collection sweep, resolving circular references and releasing the associated tensors back to the PyTorch memory pool.

### 5.5 Model Inter-Training Memory Release

```python
    tf_epoch_losses, tf_batch_losses = train_model(
        model=transformer,
        loader=loader,
        ...
    )
    
    # ── Memory management rails: clean RAM completely before baselines ────────
    log.info("Cleaning memory from Transformer allocation...")
    del transformer, optimizer_tf
    gc.collect()
```

#### Operational Mechanics
Before allocating and training the second model (`CDLinearBaseline`), the first model (`LinearGridForecaster`) and its optimizer state are deleted.

1. **Optimizer Memory Footprint**:
   The AdamW optimizer stores first-moment vector $\mathbf{m}$ and second-moment vector $\mathbf{v}$ for every parameter:
   $$\text{Optimizer Memory} \approx 2 \times \text{Parameter Count} \times 4 \text{ bytes}$$
   For the Transformer, this optimizer state overhead is significant.
2. **Sequential RAM Optimization**:
   By deleting `transformer` and `optimizer_tf` and calling `gc.collect()`, we free this memory before allocating `cdlinear` and its optimizer. This keeps peak RAM usage lower during the training run.
